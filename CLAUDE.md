# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Mondrian is an Olap4j-based OLAP (ROLAP) server written in Java: it compiles and evaluates MDX queries against a
relational database, aggregating results through a segment/aggregation cache. This repository (`SergeiSemenkov/mondrian`,
branch `eMondrian`) is a personal fork of Pentaho's community Mondrian, carrying its own patch series on top of
upstream `master` (subcube filtering/pushdown, a Redis-backed segment cache with TTL, dynamic servlet registration,
XMLA/DAX compatibility fixes). Version strings follow `9.3.0-emondrian.N`; bump `N` in `mondrian/pom.xml` when cutting
a new patch.

## Modules

Maven multi-module build, root `pom.xml` (packaging `pom`), inheriting from the external parent
`org.pentaho:pentaho-ce-jar-parent-pom`:

- **mondrian** — the core OLAP engine (the module that matters for almost all changes).
- **workbench** — a Swing desktop GUI for authoring Mondrian schema XML.
- **assemblies/psw-ce** — packages the deployable distribution zip.

## Build & test

Requires JDK 17, Maven 3.3+, Docker (only if running integration tests without a real MySQL instance). The
project is pinned to Java 17 via `source.jdk.version`/`target.jdk.version`/`maven.compiler.release` overridden in
the root `pom.xml` (the external `pentaho-ce-jar-parent-pom`/`pentaho-parent-pom` ancestors default these to 8).

```bash
# Full build, no integration tests
mvn install

# Full build + integration tests against a disposable Dockerized MySQL + Foodmart dataset
mvn -DrunITs -P embedded-mysql,load-foodmart install -Djava.locale.providers=COMPAT,SPI

# Run a single integration test class
mvn verify -DrunITs -Dit.test=NonEmptyTest.java -DfailIfNoTests=false -Djava.locale.providers=COMPAT,SPI

# Regenerate mondrian.properties.template / property docs only
mvn generate-sources
```

Notes:
- There is no `src/test`; all tests live under `mondrian/src/it/java/mondrian/**` and run as Failsafe integration
  tests (`-DrunITs`), not Surefire unit tests. Test classes named `*Test.java`; `mondrian/src/it/java/mondrian/test/Main.java`
  is the umbrella suite entry point.
- To point tests at an existing database instead of Docker MySQL, create a `mondrian.properties` file at the repo
  root with `mondrian.foodmart.jdbcURL` / `jdbcUser` / `jdbcPassword` — its presence disables the `embedded-mysql`
  profile. Activate `load-foodmart` to (re)populate that database from the Foodmart loader before tests run.
- `mvn -Pcmdrunner` builds and launches `mondrian.tui.CmdRunner`, an interactive MDX query console useful for manual
  debugging; it requires `mondrian.properties` (`mondrian.catalogURL` should point at `../demo/FoodMart.xml`) and does
  not work against the embedded/Docker MySQL profile.

## Code generation (important before reading "missing" symbols)

A large amount of `mondrian` core code does not exist in `src/main/java` — it's generated into `mondrian/src/generated/`
by the `generate-sources` Maven phase (Ant target defined in `mondrian/build.xml`) and added as an extra source root.
If a symbol can't be found under `src/main/java`, check `src/generated/java` (present in the working tree after a
build) or the source template that produces it:

- `mondrian/olap/MondrianDef.java` — generated by eigenbase `xomgen` from `mondrian/olap/Mondrian.xml` (this XML is
  effectively the Mondrian schema XSD/DTD source of truth for cube/dimension/hierarchy schema elements).
- `mondrian/rolap/aggmatcher/DefaultDef.java` — generated from `mondrian/src/main/resources/DefaultRulesSchema.xml`.
- `mondrian/xmla/DataSourcesConfig.java` — generated from `mondrian/xmla/DataSourcesConfig.xml`.
- `mondrian/resource/MondrianResource.java` (+ locale variants) — generated by eigenbase `resgen` from
  `mondrian/resource/MondrianResource.xml`; this is how MDX/engine error messages and their locale text are defined.
  To add or change a user-facing exception message, edit that XML, not a `.java` file.
- `mondrian/olap/Parser.java` / `ParserSym.java` — generated by JavaCUP from `mondrian/olap/Parser.cup` (legacy parser).
- `mondrian/parser/MdxParser*.java` — generated by JavaCC from `mondrian/parser/MdxParser.jj` (current MDX grammar/parser;
  edit the `.jj` file to change MDX syntax support).
- `mondrian/util/PropertyUtil` generates `MondrianProperties.java` from properties declared in `mondrian/olap/` —
  the source of all `mondrian.properties` runtime configuration keys.

## Architecture

Request flow: an MDX string enters through `mondrian.olap.Connection`/`mondrian.olap4j` (olap4j driver, registered via
`META-INF/services/java.sql.Driver`), is parsed by the JavaCC grammar (`mondrian.parser`) into an AST
(`mondrian.mdx`/`mondrian.olap` expression types), resolved and compiled into executable form
(`mondrian.calc`, package of `Calc` implementations returned by `ExpCompiler`), then evaluated by `mondrian.rolap`
against the schema loaded from `mondrian.olap.MondrianDef`.

- **mondrian.olap** — core metamodel and public API: `Connection`, `Cube`, `Schema`, `Query`, `Exp`, `Axis`, roles/access
  control. This is what embedding applications talk to.
- **mondrian.mdx** — MDX parse-tree node types (some legacy node types still live in `mondrian.olap`, e.g. `Exp`,
  `Literal`).
- **mondrian.calc** — compiled-expression layer; `ExpCompiler` turns resolved MDX expressions into `Calc` objects
  (`impl/` has the concrete implementations) that get evaluated per cell/tuple during query execution.
- **mondrian.rolap** — the relational data-access layer implementing the above against a JDBC source; this is where
  most engine logic and most of the fork's custom patches live. Key concepts:
  - `MemberReader` (per-dimension; `SmartMemberReader` is the common case) resolves member/hierarchy navigation
    (`member.children`, etc.) via the `RolapSchemaReader`.
  - Cell evaluation is two-phase: `FastBatchingCellReader` records `CellRequest`s instead of hitting the DB
    immediately; once a batch of requests is collected, `rolap.agg` (`Aggregation`, `AggregationManager`,
    `Segment`/`SegmentWithData`) issues batched SQL and populates the segment cache.
  - `rolap.aggmatcher` — matches/loads pre-built aggregate tables declared in schema.
  - `rolap.sql` — SQL generation helpers (`SqlQuery`, cross-join/tuple/member constraints) used to build the queries
    issued to the underlying RDBMS.
  - `rolap.cache` — segment cache indexing; pluggable external caches implement `mondrian.spi.SegmentCache` (this
    fork adds a Redis-backed implementation with TTL support — see the `redis.clients:jedis` dependency).
- **mondrian.spi** — the extension points implementers plug into: `Dialect` (one implementation per supported RDBMS,
  registered in `META-INF/services/mondrian.spi.Dialect` — check/extend this file and `spi.impl` when adding database
  support), `UserDefinedFunction` (see `mondrian.udf` for built-in UDF examples and
  `META-INF/services/mondrian.spi.UserDefinedFunction`), `SegmentCache`, `DynamicSchemaProcessor`, `DataSourceResolver`.
- **mondrian.xmla** — XML for Analysis (SOAP/XMLA) server implementation (`XmlaServlet`, `XmlaHandler`), the protocol
  used by Excel/Power BI-class clients; `MondrianModuleServletRegistrar` supports dynamic servlet registration (a
  fork-specific addition).
- **mondrian.server** — server-mode concerns layered on top of the embeddable engine: session/statement/execution
  lifecycle (`Session`, `Statement`, `Execution`, `Locus`), repository of catalogs (`Repository` and its
  `FileRepository`/`UrlRepositoryContentFinder` implementations), JMX monitoring (`server.monitor`).
  `MondrianServerVersion` (generated) carries the build's version/schema-version constants.
- **mondrian.metrics** — Prometheus metrics hooks (connection/execution/session/memory counters).
- **mondrian.tui** — headless test/debug tooling, notably `CmdRunner` (interactive MDX shell) and mock servlet
  classes used by XMLA tests.
- **mondrian.util / mondrian.recorder** — general utilities and a small `MessageRecorder` abstraction used for
  collecting warnings/errors during schema validation.

Dialect and RDBMS-specific SQL generation quirks are one of the most-touched areas across the git history — when
fixing a query-generation bug, check whether it's dialect-specific (`spi.impl.*Dialect`) before changing shared
`rolap.sql`/`rolap.agg` code.

### Drillthrough columns: attribute-based vs. level-based

`<Cube>` can declare a `<DrillThroughAction>` (`mondrian.olap.Mondrian.xml`, `RolapCube.addActions`) — a named,
schema-configured list of columns returned by a DRILLTHROUGH request, built from `<DrillThroughAttribute>` /
`<DrillThroughMeasure>` children. There are two ways to point a `<DrillThroughAttribute>` at a column, and they are
not equivalent:

- **`sourceAttribute="..."`** (current) — names a `DimensionAttribute` of `dimension="..."` directly and binds to
  its `KeyColumn`, independent of any hierarchy/level. This is the only way to reference a property-only attribute
  (`attributeHierarchyEnabled="false"`, e.g. FoodMart's `Store Manager`/`Store Type`/`Store Sqft`), which has no
  `Level`/`Hierarchy` of its own at all. Resolved in `RolapCube.resolveDrillThroughAttributeColumn`, which builds a
  `RolapStar.Column` via the new level-less `RolapStar.Table.makeColumnForAttributeExpr` and wraps it in
  `RolapDrillThroughAttributeColumn` (a synthetic `OlapElement`, never exposed to MDX/XMLA, consumed only by
  `RolapAggregationManager.addNonConstrainingColumns`'s dedicated branch). **Use this for every new/attribute-based
  cube.**
- **`dimension`/`hierarchy`/`level="..."`** (obsolete) — resolves a real `Level` object and reads its
  `getBaseStarKeyColumn(...)`. Still fully supported — including transparently for a browsable attribute hierarchy's
  auto-generated level, since that's just an ordinary `RolapLevel` (see the "why" doc below) — but kept only so
  schemas written before `sourceAttribute` existed keep loading and behaving unchanged. Don't use it in new schema
  examples.

See `emondrian-modules/context/attribute_implementaion.md` (in the sibling `emondrian-modules` repo) for the
broader `DimensionAttribute` model this builds on — why attributes generate levels the way they do, and the traps
around binding a column to the dimension's own table instead of `Level.table`.

## Configuration

Runtime behavior is controlled by `mondrian.properties` (Java properties file), whose keys are declared as fields in
`mondrian/olap/MondrianProperties.java` (generated — see Code generation above) via `PropertyUtil`. Run
`mvn generate-sources` and inspect `target/mondrian.properties.template` for the full, documented list of supported
properties rather than guessing at key names.
